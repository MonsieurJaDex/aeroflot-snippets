VERDICT: CONFIRMED, and it is deliberate in code, not an accident of one call:
  track.rs:453-455 does `redis_conn.set(&key, stored.to_string())` — plain SET.
  `set_ex` appears in this crate only in src/utils.rs (lines 41,47,53,59,65), never in track.rs.
  So `map:{id}:track:{obj}` holds exactly one key per spelling of obj, growth is bounded by
  the number of distinct trackers, and it is never evicted by expiry. The row is stale after
  location.stale_after_secs = 45 but the key survives forever; readers must judge freshness by
  the stored `t`, which is what the stale key in the dumps is doing. The positional keys
  (`position:…`, `position_ts:…`) are equally permanent, so a decommissioned engineer's last
  position is readable forever too. That is a design choice worth confirming, not a leak:
  the key space does not grow per point, only per object.

VERDICT: REAL DIVERGENCE, three separate effects, all from `obj` entering keys verbatim:
  a) `map:{id}:track:{obj}` is keyed by the raw string (track.rs:374) — two spellings of one
     engineer are two keys, each with its own `t` comparison (track.rs:380). Neither key ever
     sees the other's timestamp, so out-of-order delivery between the two sources is accepted.
  b) `position_id` (track.rs:456) is the parsed UUID with format specifiers dropped, so both
     spellings write the SAME `map:{id}:position:{uuid}`. That key therefore received the
     00:02:00 point of x=0,y=63 AFTER the 00:05:00 point of x=25,y=22 — the shared position
     for dispatch regressed, because the stale-point guard sits on the per-spelling track key
     and not on position_id. This is the only one of the three that corrupts a shared value;
     `position:{uuid}` is what dispatch and ops read (src/router/mod.rs:463,1782, src/router/ops.rs:723).
  c) `calibration::load(redis_conn, &active.id, &obj)` (track.rs:440) also uses the raw obj:
     a pin saved for the canonical spelling is silently ignored by the other spelling.
     Observed: pin [7,9] on lowercase → x=7,y=9; same raw GPS under UPPERCASE → x=25,y=22 (snap).
  d) v5 fallback is stable, for the record: `Uuid::new_v5(NAMESPACE_OID, obj.as_bytes())`
     reproduced exactly — e-01 → 6870cc1a-124f-52e8-936d-295beadfba4b,
     v-01 → dd8706e0-e60d-52b4-8805-31c53aa1ab89, RA-73142 → 62313260-2831-590b-9b13-fd65bbdd765a.
     So the divergence is spelling-only (case/format), not a different hash.
  Practical risk is low unless a tracker switches its `obj` spelling mid-life, but the fix is
  cheap: key the track record and the pin by the canonical `position_id` (or lowercase/NFC
  `obj` once, at the top of apply_point, before any key is built).

ADDITIONAL OBSERVATIONS FROM THE SAME RUN (not asked for, relevant to "correctly")
================================================================================
* Outlier gate never runs on the first point of an object. track.rs:376-393 wraps both the
  stale check and `outlier(...)` in `if let Some(raw) = &previous`, so a brand-new object is
  stored without any range check:
    $ POST {"obj":"RA-73142","lat":55.8300,"lon":37.6380,"t":"2026-11-25T00:00:00.000Z","acc":9999}
    {"accepted":true,"applied":true,…}
    $ redis-cli -n 9 GET map:map2:track:RA-73142
    {"acc":9999.0,"lat":55.83,"lon":37.638,"spd":null,"t":"2026-11-25T00:00:00.000Z","x":25,"y":22}
  With a stored point, the same acc is rejected: `acc:500 > max_accuracy_m 80` →
  {"applied":false}, value byte-identical. Same for a 3 km jump in 1 s (max_speed_mps 12) →
  {"applied":false}, value byte-identical.
* Equal `t` is applied, overwriting: with `old > when` strict, an identical timestamp passes
  the guard. Proof with identical coordinates so the speed rule cannot fire:
    $ POST {"obj":"e-01","lat":55.8290,"lon":37.6390,"t":"2026-11-25T01:01:00.000Z","acc":5,"spd":0}
    {"accepted":true,"applied":true,…}   -> value re-written, spd now 0.0
  (My first attempt at this returned applied:false — that was the speed rule, not equality:
   different coordinates at a 0 s gap are infinitely fast.)
* Snap failure writes nothing but journals: `lat:0,lon:0` → applied:false and the stored
  value is byte-identical.
* Journal asymmetry (postgres `journal`): `outlier` and `snap failed` both `track_rejected`;
  the stale-`t` rejection and the unknown-`obj` rejection are NOT journalled at all.
  4 rows total, exactly matching 1 accuracy + 2 speed + 1 snap rejection:
    track_rejected | e-01     | {"acc":5.0,"lat":55.832,"lon":37.637,"spd":1.0}
    track_rejected | v-01     | {"acc":500.0,"lat":55.8295,"lon":37.6385,"spd":null}
    track_rejected | v-01     | {"acc":10.0,"lat":55.8,"lon":37.5,"spd":null}
    track_rejected | RA-73142 | {"acc":5.0,"lat":0.0,"lon":0.0,"spd":null}
* A future-dated point locks out real time. Stored t=03:02:00 while the server clock was
  00:43:16 made a later, correctly-stamped point stale:
    $ POST {"obj":"v-01","lat":55.8301,"lon":37.6381,"acc":5}    (no t)
    {"accepted":true,"applied":false,…,"t":"2026-11-25T00:43:16.667Z"}
  Correct per the contract, but a tracker with a badly skewed clock freezes its own record
  until wall time catches up. Worth knowing, not a defect in `obj` handling.
* `position_ts:{uuid}` stores `when.timestamp()` (unix seconds), while the track JSON `t` is
  RFC 3339 with milliseconds — two time formats for the same instant, both UTC.
