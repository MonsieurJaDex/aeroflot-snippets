# Расчёт и приоритезация — что фронт получает после закрытия пунктов ТЗ 16–21

Дополнение к `docs/frontend-contract-b.md` (превью, назначение, переназначение,
снятие). Здесь — только то, что изменилось в контракте после закрытия пунктов
ТЗ 16, 17, 19, 20, 21. Правок во `frontend/**` эти изменения не требуют: все
новые поля добавлены, ни одно старое не переименовано и не удалено.

## 1. `POST /api/assign/candidates` и `POST /api/assign` — новое в строке кандидата

Строка `candidates[]` получила три поля; остальные прежние. Тело самого превью —
только `{ "request_id": "<uuid>" }`: `classifier_text`, `plane_uuid` и `note` —
поля `/api/assign`, и превью отвечает на них `422` (см. `frontend-contract-b.md`).

```json
{
  "engineer_id": "…", "eligible": true,
  "reason": "допуск подходит, свободен, 240 с пешком, загрузка 1, MEL B: бонус 90 с",
  "eta_seconds": 240, "uses_vehicle": false,
  "late_seconds": 0.0, "load_penalty": 20.0,
  "aog_bonus": 0.0, "arrival_bonus": 0.0,
  "urgency_bonus": 60.0, "mel_bonus": 90.0,
  "factors": [
    { "name": "eta",            "seconds":  240.0 },
    { "name": "late",           "seconds":    0.0 },
    { "name": "load",           "seconds":   20.0 },
    { "name": "aog_bonus",      "seconds":    0.0 },
    { "name": "arrival_bonus",  "seconds":    0.0 },
    { "name": "urgency_bonus",  "seconds":  -60.0 },
    { "name": "mel_bonus",      "seconds":  -90.0 }
  ],
  "score": 110.0
}
```

- `factors` — это и есть балл, разложенный на слагаемые: сумма `seconds` равна
  `score` до последнего бита. Штраф положительный, бонус отрицательный.
  Состав всегда один и тот же (семь имён выше), поэтому таблицу можно рисовать
  фиксированными колонками; у отклонённого кандидата `factors` пустой.
- `urgency_bonus` — сколько секунд снято за `urgent`; `0` у `normal`.
- `mel_bonus` — сколько секунд снято за категорию MEL (`A` > `B` > `C` > `D`);
  `0`, если категория не объявлена.
- `score = eta_seconds + late_seconds + load_penalty - aog_bonus
  - arrival_bonus - urgency_bonus - mel_bonus`. Меньше — лучше.
- `reason` теперь перечисляет всё, что вошло в балл: допуск, свобода, время и
  способ (пешком/спецтранспорт), загрузка, нужен ли склад, AOG, прилёт,
  срочность, MEL. Показывать его как есть в подсказке строки.

Для UI достаточно: колонки «ETA», «Загрузка», «Бонусы» (сумма отрицательных
`seconds`), «Балл», бейджи «AOG», «прилетел», «срочно», «MEL A/B/C/D».

## 2. Источники `urgency` и MEL — те же ручки, что и раньше

- `POST /api/requests`, поле `urgency`: `"normal"` (по умолчанию) или `"urgent"`.
  Только эти два значения влияют на балл; `urgent` снимает
  `urgency_bonus_secs` (по умолчанию 60 с).
- `POST /api/tasks/current/mel`, тело `{ "category": "A"|"B"|"C"|"D",
  "defer_until": "<RFC3339>"|null }` — ставит категорию текущей задачи
  инженера; она сразу попадает в балл (по умолчанию A 120, B 90, C 60, D 30 с).

## 3. `POST /api/tasks/current/waiting-part` — инженер возвращается в пул (п.19)

Ответ прежний (`200`). Изменилось состояние: задача остаётся открытой
(`status = "waiting_part"`, `waiting_part = true`, считается в загрузке), но
`assigned_engineer` очищается — инженер снова доступен для других заявок и
сразу появляется в превью как `eligible`. Экрану инженера не нужно заново
«принимать» задачу, чтобы вернуться: он просто в пуле; когда запчасть пришла,
диспетчер назначает заново — `POST /api/requests/{id}/reassign` с телом
`{ "engineer_id": "…", "reason": "запчасть пришла" }` (поле `reason`
обязательно, иначе `422`). Этот вызов и есть выход из `waiting_part`: он
снимает `waiting_part`, ставит инженера и пересчитывает прогноз. `GET
/api/tasks/current` у ожидающего инженера отвечает `403` — это ожидаемо, задачи
у него больше нет.

## 4. Живой прогноз по GPS (п.20)

`POST /api/v1/track` (и `GET /api/v1/track`) обновляют теперь не только
позицию, но и прогноз по открытой задаче инженера: при переходе в новую клетку
карты пересчитывается `tasks.eta_seconds`, а `sla_risk` / `sla_breached` пишутся
в журнал только в момент перехода в это состояние.

Контракт ответа не изменился — ровно `{ "accepted", "applied", "obj", "t" }`,
поле за полем. То есть GPSLogger и текущий фронт работают без правок.
Пересчёт идёт максимум один раз на клетку, а не на каждую точку пакета, и
ошибка пересчёта не отменяет уже принятую точку.

Показывать: `GET /api/tasks/current` → `eta_seconds` можно обновлять по своему
таймеру, значение меняется само по мере движения инженера.

## 5. `GET /api/alerts` — предупреждение с альтернативой (п.21)

```json
{ "alerts": [ {
    "request_id": "…",
    "message": "не успевает, прогноз 300 с; успевает инженер <uuid>",
    "alternative_engineer_id": "<uuid>",
    "alternative_margin_seconds": 120
} ] }
```

- `alternative_engineer_id` — лучший инженер пула (не тот, кто держит заявку),
  чей собственный путь всё ещё укладывается в дедлайн; `null`, если замены нет.
- `alternative_margin_seconds` — запас этого инженера в секундах (положителен,
  когда замена успевает). Если замены нет, здесь остаётся прежний запас самой
  задачи.
- В UI: рядом с предупреждением — кнопка «Передать этому инженеру», ведущая на
  `POST /api/requests/{id}/reassign` с `engineer_id` из
  `alternative_engineer_id`.
